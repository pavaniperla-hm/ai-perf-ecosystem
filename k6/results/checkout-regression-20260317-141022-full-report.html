🔍 Root Cause Analysis

  • Threshold breach
    p95 = 52.69 ms — 2.07× above the 25.5 ms limit
    The overall p95 response time exceeds threshold by more than 2×. Thresholds were intentionally set tight (25.5 ms) to trigger regression on real network latency.
  • Latency distribution
    Uniform latency across all 5 transactions (51–62 ms)
    txn_user_login: 54 ms, txn_products_list: 54.25 ms, txn_product_detail: 51.45 ms, txn_order_history: 57.15 ms, txn_create_order: 61.5 ms. No single hot transaction — all are proportionally elevated. This rules out a single slow query or endpoint as root cause.
  • Shared bottleneck hypothesis
    AKS Nginx ingress keep-alive / HTTP/2 or PostgreSQL connection pool saturation
    Uniform latency elevation is the classic signature of a shared network-layer bottleneck or a connection pool that serialises requests at low concurrency. CPU and memory are well within limits (all pods <10 m CPU, <65 Mi memory).
  • Highest-latency transaction
    txn_create_order p95 = 61.5 ms (marginal vs 60 ms threshold)
    POST /api/orders is the most expensive transaction. Candidate: missing index on user_id / product_id in order-db. Recommend running EXPLAIN ANALYZE to confirm.
  • Infrastructure alert
    Open Dynatrace problem: "No pod ready" (INFRASTRUCTURE impact)
    This problem is outside the test window and correlates with the 3 restarts seen on order-service, product-service, and user-service. Not a current blocker but warrants investigation.
  • Errors & application health
    Zero errors, zero log anomalies
    0% HTTP error rate, 100% check pass rate, 0 Loki error events. The application is functionally healthy — the regression is a performance regression only, not a reliability incident.
Primary Verdict: Performance regression confirmed. p95 = 52.69 ms exceeds the 25.5 ms threshold by 2.07×. Uniform latency pattern across all transactions points to a shared infrastructure bottleneck (AKS ingress or DB connection pooling), not a single defective endpoint. No functional errors detected.

✅ Next Steps

  1. Profile POST /api/orders — check order-db query plan for missing indexes
    txn_create_order is the highest latency transaction at p95=61.5 ms. Run EXPLAIN ANALYZE SELECT ... FROM orders WHERE user_id=? AND product_id=? in order-db to identify missing indexes. Expected fix: add composite index on (user_id, product_id).
  2. Investigate AKS Nginx ingress keep-alive and PostgreSQL connection pool saturation
    Uniform latency across all 5 transactions (51–62 ms) points to a shared bottleneck. Check Nginx ingress controller configuration for keep-alive timeout and HTTP/2 settings. Also check pg connection pool size in each service's environment config vs number of concurrent VUs (20).
  3. Investigate open Dynatrace infrastructure problem "No pod ready"
    3 restarts on order-service, product-service, user-service within last 43 min. Review pod restart reason: kubectl describe pod -n perf-demo <pod-name>. Could indicate OOMKill, liveness probe misconfiguration, or intermittent startup failure.
  4. Verify Promtail DaemonSet log shipping is healthy
    kubectl get pods -n perf-demo | grep promtail — currently Running (1/1, 0 restarts, 45 min uptime). Confirm Loki is receiving logs from perf-demo namespace by querying Grafana Explore with {namespace="perf-demo"} without the error filter.

    Current token only has metrics.ingest scope. Create a new token with metrics.read added to enable DT response time breakdown and DB time % in the analysis agent. Update DYNATRACE_API_TOKEN in .env and the dynakube k8s secret.
